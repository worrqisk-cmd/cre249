# Каталог и админка: установка

Рабочий проект Supabase: `bvlcyhcuneaphuletnqz`. Публичный сайт остаётся Angular SPA под `/cre249/`, административный вход — `#/admin/login`. Пароль и токены в репозитории не хранятся. Publishable key, URL, UID и email в `site-config.json` публичны и не дают прав владельца; доступ определяют RLS и Supabase Auth.

## 1. Проверка проекта и схема

Перед SQL проверьте project ref в адресе Supabase Dashboard: **bvlcyhcuneaphuletnqz**. В SQL Editor сначала проверьте существующие таблицы `public.categories`, `public.products`, `public.site_settings`, bucket `milana-catalog` и политики `storage.objects`. Миграция использует `if not exists` для таблиц и не удаляет строки, однако одноимённые политики и триггеры она заменяет. Если объекты уже существуют с другой структурой, сравните их вручную до запуска.

Запустите целиком [основную миграцию](supabase/migrations/20261005190000_catalog.sql), затем [первичный импорт](supabase/seed.sql), затем [миграцию архива](supabase/migrations/20261005232000_archive_galleries_and_drafts.sql). Повторный seed использует `on conflict do nothing`: не создаёт дубликаты и не меняет уже отредактированные товары. Seed оставляет цену и наличие неподтверждёнными, а WhatsApp и Telegram пустыми до проверки владельцем. Миграция архива добавляет галереи восьми опубликованным изделиям и 17 скрытых черновиков. У форели и тарта остаётся заглушка.

Учётная запись Supabase Auth с email `mind.style11@gmail.com` должна уже существовать и иметь UID `7ff37aab-19f3-46c0-8842-a28381902bca`. Если UID другой, сначала измените UID во всех RLS/Storage политиках миграции и в конфигурации приложения, затем применяйте схему. Одной замены логина или email недостаточно. Не включайте регистрацию посетителей ради админки.

## 2. Локальная конфигурация и запуск

Node 22.22.3, pnpm 12.8.1. `pnpm install --frozen-lockfile`. Скрипт `scripts/configure.mjs` берёт публичные значения из переменных среды, затем `.env.local`, затем `.env.example`; перед `pnpm start --port 8446` и `pnpm build` он создаёт `public/site-config.json`. Файл игнорируется Git. `pnpm preview:pages` обслуживает сборку по `http://127.0.0.1:8447/cre249/`. Не копируйте secret/service_role key в конфигурацию браузера. Чтобы сменить проект, обновите проверку project ref в `scripts/configure.mjs`, импортёре, миграции и настоящие политики проекта осознанно; текущие скрипты специально отказываются работать с другим URL.

После применения схемы откройте публичный каталог и `#/admin/login`. Логин `milana` сопоставляется с email в клиенте; введённый пароль проверяет Supabase Auth. Route guard скрывает интерфейс от других пользователей, а политики базы ограничивают данные и изменения конкретным UID. Выход завершает сессию. Редактирование каталога отражается после нового запроса или перезагрузки страницы; Realtime не включён.

## 3. Фотографии

Полный разбор 123 полноразмерных снимков, подписей сообщений и соответствий выбранным файлам сайта находится в [реестре архива](guidelines/PHOTO_ARCHIVE.md). Telegram также содержит уменьшенные копии; они не считаются отдельными фотографиями.

Первичные фотографии 12 изделий и 25 кадров скрытых черновиков загружены в приватный Storage. Дополнительные кадры опубликованных изделий лежат в `public/photos/` и входят в сайт. Исходные кадры скрытых черновиков лежат в `catalog-assets/drafts/` и **не входят** в сборку. Повторный `pnpm import:photos` пропускает уже привязанные файлы. Новые фото админка помещает в bucket `milana-catalog` по пути `products/<uuid>/<uuid>.<ext>`; загрузка, замена и удаление разрешены только UID владельца. Публичный клиент может создать ссылку на 10 минут лишь для файла, упомянутого опубликованным изделием. Уже выданная ссылка остаётся рабочей до истечения срока при последующем скрытии изделия; если нужна мгновенная отзывность, потребуется другая схема выдачи изображений. Скрытая запись не доступна через Data API или прямую публичную ссылку на товар.

Для фотографий скрытых черновиков задайте пароль владельца **только в окружении команды** и выполните `read -s SUPABASE_ADMIN_PASSWORD; export SUPABASE_ADMIN_PASSWORD; pnpm import:photos; unset SUPABASE_ADMIN_PASSWORD` локально. Скрипт проверяет UID, пропускает уже импортированные фото и не перезаписывает существующий файл. Не помещайте пароль в `.env.local`, историю команд или чат.

Для проверки открытия всех 25 скрытых фотографий под настоящей сессией владельца выполните с тем же безопасным вводом пароля `pnpm check:owner-photos` вместо `pnpm import:photos`. Проверка не изменяет данные и выводит только количество доступных файлов.

## 4. Проверка доступа

После применения схемы проверьте Data API и Storage от трёх субъектов: anon, owner UID и другого authenticated UID. Для воспроизводимой проверки задайте краткоживущие `OWNER_ACCESS_TOKEN` и `OTHER_ACCESS_TOKEN` из реальных сессий Supabase Auth **только в окружении процесса** и выполните `pnpm check:access`. Альтернатива в локальном zsh без копирования токенов: задайте `OTHER_TEST_EMAIL` для отдельного тестового пользователя Auth, затем введите пароли скрыто и запустите команду:

```sh
read -s SUPABASE_ADMIN_PASSWORD; export SUPABASE_ADMIN_PASSWORD
read -s OTHER_TEST_PASSWORD; export OTHER_TEST_PASSWORD
pnpm check:access
unset SUPABASE_ADMIN_PASSWORD OTHER_TEST_PASSWORD
```

Скрипт сначала сверяет UID обоих JWT через Auth, затем проверяет чтение скрытого товара, создание, изменение и удаление изделия, загрузку, замену и удаление файла, выдачу ссылки для опубликованного и скрытого фото. Тестовую запись он удаляет в `finally`. Токены и пароли не записываются и не печатаются. Один route guard не доказывает права в базе. Не проводите проверку владельца через SQL Editor без смены роли: его привилегии обходят RLS.

## 5. Что требуется владельцу

Применить SQL и seed, если нет авторизованного MCP/CLI; подтвердить номер WhatsApp, при желании Telegram и условия получения в настройках; проверить email/UID Auth и ввести пароль в форме. Исторические цены и наличие не импортированы.

На 5 октября 2026 года доступ MCP к проекту восстановлен. Обе миграции и seed применены: 4 категории, 32 товара, 14 опубликованы, 18 скрытых черновиков. В приватном bucket 37 файлов: 12 доступны анонимному посетителю для опубликованных товаров через подписанные ссылки, 25 принадлежат скрытым черновикам. Проверены реальные RLS через роли SQL и анонимный Data API: скрытые товары и их фото недоступны, запись и загрузка anon отклонены, владелец по UID видит все 37 объектов. Chromium прошёл публичный сценарий на настоящих данных. Проверка `pnpm check:access` с двумя настоящими Auth-сессиями остаётся отдельным шагом: для неё нужен тестовый пользователь, отличный от владельца.
