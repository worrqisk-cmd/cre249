# Обычные URL и GitHub Pages

Angular 22.2.1 поддерживает `outputMode: static` и `RenderMode.Prerender`: https://angular.dev/guide/hybrid-rendering. В проект добавлены platform-server и ssr той же версии. Сервер в production не нужен. Публикуется только `dist/milana-angular/browser`, не server bundle.

Маршруты: `/cre249/`, `/cre249/catalog/`, `/cre249/catalog/<category>/`, `/cre249/item/<slug>/`, `/cre249/admin/login/`. Ссылки сериализуются с завершающим `/`. Старые `#/catalog`, `#/catalog/<category>`, `#/item/<slug>`, `#/admin/login` заменяются через history.replaceState до запуска роутера. Интро определяется по pathname и проигрывается только при полной загрузке главной, с учётом reduced motion.

`pnpm build` создаёт публичную конфигурацию, читает Supabase с publishable key и фильтрами published/is_public, проверяет точное количество строк, обязательные настройки и связь категорий, скачивает только фотографии опубликованных изделий, затем запускает настоящий Angular prerender. Повторное чтение перед рендером обнаруживает изменения каталога во время подготовки. Ошибка API, фотографии, пустой/усечённый каталог или неполный HTML завершает команду ненулевым кодом; workflow не загружает и не публикует такой artifact. Каталог намеренно нельзя опубликовать полностью пустым без изменения этой политики.

Прямой HTTP-вход получает готовое содержимое, уникальные title/description и canonical. Переход из карточки открывает диалог с прежними начинками, сообщением, WhatsApp, Escape, Back/Forward и возвратом фокуса/прокрутки. Прямой вход открывает обычную страницу изделия с теми же действиями. Клиент после запуска заново читает актуальный публичный каталог; hydration не включена, поэтому во время этого запроса возможен краткий loading. На GitHub Pages неизвестный URL получает HTTP 404 и простую страницу `404.html`, без перенаправления. Новые изделия до следующей публикации доступны внутри приложения, но их прямой URL ещё возвращает 404.

Админка `/admin/login/` и `/admin/` имеет собственные статические оболочки без данных владельца и `noindex, nofollow`, не входит в sitemap. Supabase Auth, route guard и RLS остаются прежними. Пароли, сессии и service_role не используются при сборке. В клиенте остаются только прежние публичные параметры Auth. Кнопка входа на публичных страницах не добавлялась.

## Обновление после правок в Supabase

1. Завершите изменения каталога, включая published, категории, тексты и фотографии.
2. Выполните `pnpm install --frozen-lockfile`, `pnpm test --watch=false`, `pnpm build`.
3. Запустите `pnpm preview:pages`, затем `pnpm test:routing` (Chromium, без медиа). Дополнительно доступны проверки ошибок API и формы администратора.
4. После отдельного разрешения публикации публикуйте весь новый browser artifact через существующий Pages workflow. Push в main автоматически запускает публикацию; workflow_dispatch на main также публикует. PR только собирает/проверяет. Изменение базы само по себе workflow не запускает.

**Снятие с публикации:** сначала published=false в Supabase, затем сразу полная пересборка и замена Pages artifact. Новая сборка удаляет прежние HTML, ссылки sitemap и сгенерированные фотографии снятого изделия. Старый статический HTML и копия фото остаются публичными до замены artifact; браузерные/CDN-кеши и внешние копии мгновенно отозвать нельзя. До пересборки клиент скрывает изделие после актуального API-запроса, но HTTP-HTML всё ещё содержит старую страницу. Изображения из приватного Storage копируются в публичный artifact лишь пока изделие опубликовано; подписанные URL и Storage-токены в HTML не сохраняются. Это необходимый компромисс устойчивых статических фото, требующий своевременной пересборки при снятии публикации. Исторические файлы `public/photos/` не удаляются автоматически: при отзыве такого кадра удалите его из public вручную и пересоберите.

Снимок, маршруты и скачанные фото игнорируются Git; публикуется сгенерированный artifact, а не снимок базы в исходном репозитории. Не запускайте отдельное `ng build` для публикации: оно может использовать старый локальный снимок. Канонический origin сейчас `https://worrqisk-cmd.github.io`; при смене домена обновите Seo и finalize-static.

## Проверки реализации 7 октября 2026

Начальное дерево main было чистым, работа выполнена в `feat/static-public-urls` от текущего main, сохранив уже объединённые каталог, публичный UI и интро. Никаких изменений Supabase не выполнялось. Локальная production-сборка Angular 22.2.1, Node 22.22.3, pnpm 12.8.1; статический сервер 127.0.0.1:8447/cre249 без SPA fallback. Публичные запросы без сессии, Chromium headless 390×900 и 1440×900, без throttling и записи медиа.

- `pnpm build`: 23 публичных документа (17 опубликованных изделий, 4 категории, каталог, главная), валидированные canonical и содержимое, sitemap и две оболочки админки. Начальные JS+CSS 481,90 КБ, оценка передачи 118,90 КБ.
- `pnpm test --watch=false`: 4 теста прошли.
- `pnpm test:routing` / `pnpm test:e2e`: HTTP 200 всех 23 страниц, уникальные title, canonical, содержимое изделия до JS, HTTP 404 неизвестного URL, sitemap без админки; reload каталога, категории, изделия и входа; старые hash-ссылки; anon guard; Escape, Back/Forward, возврат фокуса и прокрутки; начинки, ручной текст и WhatsApp; интро только полной загрузки главной. Основной диалоговый сценарий проверен с reduced motion.
- `pnpm test:catalog-api`: ошибка, пустой ответ, published-фильтр и скрытое изделие; `pnpm test:admin-form`: Auth/форма с моками, однократное сохранение при двойном клике и unsaved guard.
- Отдельный запуск подготовки с заведомо недействительным publishable key подтвердил ненулевой выход при ошибке API; конфигурация восстановлена. Пароль владельца и изменения production не использовались.

GitHub Pages после реальной публикации не проверялся: push и публикация не выполнялись. Успешный вход настоящего владельца, физические мобильные устройства, скринридеры и полевые Core Web Vitals не проверялись. Краткая повторная загрузка данных на клиенте и задержка отзыва статического содержимого до пересборки описаны выше. Исторические `browser-check.mjs` и визуальные/анимационные сценарии с ожиданием hash URL не являются проверкой новых URL; основной e2e entrypoint переключён на `static-routing-check.mjs`.

При повторных запусках были таймауты ожидания клиентских данных: один прогон совпал с пересборкой artifact, другой ожидал каталог в проверке интро. Отдельный прямой вход изделия загрузился без browser errors. Проверка интро теперь ждёт свою навигационную ссылку, а проверки каталога по-прежнему ждут реальные карточки.
