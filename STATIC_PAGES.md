# Обычные URL и GitHub Pages

Angular 22.2.1 поддерживает `outputMode: static` и `RenderMode.Prerender`: https://angular.dev/guide/hybrid-rendering. В проект добавлены platform-server и ssr той же версии. Сервер в production не нужен. Публикуется только `dist/milana-angular/browser`, не server bundle.

Маршруты: `/`, `/catalog/`, `/catalog/<category>/`, `/item/<slug>/`, `/admin/login/`. Ссылки сериализуются с завершающим `/`. Старые `#/catalog`, `#/catalog/<category>`, `#/item/<slug>`, `#/admin/login` заменяются через history.replaceState до запуска роутера. Интро определяется по pathname и проигрывается только при полной загрузке главной, с учётом reduced motion.

`pnpm build` создаёт публичную конфигурацию, читает Supabase с publishable key и фильтрами published/is_public, проверяет точное количество строк, обязательные настройки и связь категорий, скачивает только фотографии опубликованных изделий, затем запускает настоящий Angular prerender. Повторное чтение перед рендером обнаруживает изменения каталога во время подготовки. Ошибка API, фотографии, усечённый каталог или неполный HTML завершает команду ненулевым кодом; workflow не загружает и не публикует такой artifact. Пустой каталог допустим при точном count=0, чтобы скрытие последнего товара удаляло его статические страницы.

Прямой HTTP-вход получает готовое содержимое, уникальные title/description и canonical. Переход из карточки открывает диалог с прежними начинками, сообщением, WhatsApp, Escape, Back/Forward и возвратом фокуса/прокрутки. Прямой вход открывает обычную страницу изделия с теми же действиями. Клиент после запуска заново читает актуальный публичный каталог; hydration не включена, поэтому во время этого запроса возможен краткий loading. На GitHub Pages неизвестный URL получает HTTP 404 и Angular shell `404.html`, без перенаправления: опубликованный новый slug доступен через клиент даже до prerender, но HTTP остаётся 404 и noindex. Новые изделия до следующей публикации доступны внутри приложения, но их прямой URL ещё возвращает 404.

Админка `/admin/login/` и `/admin/` имеет собственные статические оболочки без данных владельца и `noindex, nofollow`, не входит в sitemap. Supabase Auth, route guard и RLS остаются прежними. Пароли, сессии и service_role не используются при сборке. В клиенте остаются только прежние публичные параметры Auth. Кнопка входа на публичных страницах не добавлялась.

## Автоматическое обновление и ручное восстановление

С 08.10.2026 изменения публичного каталога запускают пересборку автоматически через Supabase webhook, очередь, Edge Function и Pages workflow. После сохранения в админке дополнительные действия не нужны. Черновики не запускают сборки; серия сохранений объединяется. Ниже описан ручной путь для восстановления или проверки разработки.

1. Завершите изменения каталога, включая published, категории, тексты и фотографии.
2. Выполните `pnpm install --frozen-lockfile`, `pnpm test --watch=false`, `pnpm build`.
3. Запустите `pnpm preview:pages`, затем `pnpm test:routing` (Chromium, без медиа). Дополнительно доступны проверки ошибок API и формы администратора.
4. После отдельного разрешения публикации публикуйте весь новый browser artifact через существующий Pages workflow. Push в main автоматически запускает публикацию; workflow_dispatch на main также публикует. PR только собирает/проверяет. Изменения публичного каталога также запускают workflow через подключённую очередь.

**Снятие с публикации:** сначала published=false в Supabase, затем автоматическая очередь выполняет пересборку и замену Pages artifact с debounce и проверками. Новая сборка удаляет прежние HTML, ссылки sitemap и сгенерированные фотографии снятого изделия. Старый статический HTML и копия фото остаются публичными до замены artifact; браузерные/CDN-кеши и внешние копии мгновенно отозвать нельзя. До пересборки клиент скрывает изделие после актуального API-запроса, но HTTP-HTML всё ещё содержит старую страницу. Изображения из приватного Storage копируются в публичный artifact лишь пока изделие опубликовано; подписанные URL и Storage-токены в HTML не сохраняются. Это необходимый компромисс устойчивых статических фото, требующий своевременной пересборки при снятии публикации. Исторические файлы `public/photos/` не удаляются автоматически: при отзыве такого кадра удалите его из public вручную и пересоберите.

Снимок, маршруты и скачанные фото игнорируются Git; публикуется сгенерированный artifact, а не снимок базы в исходном репозитории. Не запускайте отдельное `ng build` для публикации: оно может использовать старый локальный снимок. Канонический origin сейчас `https://milana-pechet.ru`; при смене домена обновите Seo и finalize-static.

## Проверки реализации 7 октября 2026

Начальное дерево main было чистым, работа выполнена в `feat/static-public-urls` от текущего main, сохранив уже объединённые каталог, публичный UI и интро. Никаких изменений Supabase не выполнялось. Локальная production-сборка Angular 22.2.1, Node 22.22.3, pnpm 12.8.1; статический сервер 127.0.0.1:8447/cre249 без SPA fallback. Публичные запросы без сессии, Chromium headless 390×900 и 1440×900, без throttling и записи медиа.

- `pnpm build`: 23 публичных документа (17 опубликованных изделий, 4 категории, каталог, главная), валидированные canonical и содержимое, sitemap и две оболочки админки. Начальные JS+CSS 481,90 КБ, оценка передачи 118,90 КБ.
- `pnpm test --watch=false`: 4 теста прошли.
- `pnpm test:routing` / `pnpm test:e2e`: HTTP 200 всех 23 страниц, уникальные title, canonical, содержимое изделия до JS, HTTP 404 неизвестного URL, sitemap без админки; reload каталога, категории, изделия и входа; старые hash-ссылки; anon guard; Escape, Back/Forward, возврат фокуса и прокрутки; начинки, ручной текст и WhatsApp; интро только полной загрузки главной. Основной диалоговый сценарий проверен с reduced motion.
- `pnpm test:catalog-api`: ошибка, пустой ответ, published-фильтр и скрытое изделие; `pnpm test:admin-form`: Auth/форма с моками, однократное сохранение при двойном клике и unsaved guard.
- Отдельный запуск подготовки с заведомо недействительным publishable key подтвердил ненулевой выход при ошибке API; конфигурация восстановлена. Пароль владельца и изменения production не использовались.

GitHub Pages после реальной публикации не проверялся: push и публикация не выполнялись. Успешный вход настоящего владельца, физические мобильные устройства, скринридеры и полевые Core Web Vitals не проверялись. Краткая повторная загрузка данных на клиенте и задержка отзыва статического содержимого до пересборки описаны выше. Исторические `browser-check.mjs` и визуальные/анимационные сценарии с ожиданием hash URL не являются проверкой новых URL; основной e2e entrypoint переключён на `static-routing-check.mjs`.

При повторных запусках были таймауты ожидания клиентских данных: один прогон совпал с пересборкой artifact, другой ожидал каталог в проверке интро. Отдельный прямой вход изделия загрузился без browser errors. Проверка интро теперь ждёт свою навигационную ссылку, а проверки каталога по-прежнему ждут реальные карточки.

## Индексация и обновления каталога

`public/robots.txt` разрешает обход и объявляет `https://milana-pechet.ru/sitemap.xml`. Админка не запрещена в robots.txt: робот должен прочитать `noindex, nofollow` в её статическом HTML. Это не заменяет Auth/RLS. `pnpm test:seo` проверяет публичные HTML, уникальность title/description, canonical, sitemap и директивы индексирования; workflow запускает проверку до загрузки artifact.

После изменения в Supabase названия, описания, фотографий, slug, категории, опубликованности или публичных настроек нужна новая полная `pnpm build` и публикация artifact. При изменении цены/начинок/доступности пересборка также нужна, чтобы исходный HTML соответствовал клиентскому каталогу. Публичные изменения в базе запускают GitHub Actions автоматически через очередь. Для ручного восстановления доступен `workflow_dispatch` на main либо обычный прошедший проверки push/merge в main. Не публикуйте старый локальный снимок отдельным `ng build`. При снятии изделия с публикации дождитесь успешной автоматической пересборки: до нового deploy его прежний HTML, sitemap и фото остаются публичны. После публикации сверяйте sitemap с текущим публичным API; скрытые изделия не должны присутствовать ни в sitemap, ни в директориях item artifact. Изменения в базе во время подготовки сборки приводят к отказу, а не к публикации смешанного снимка.

Подтверждение Search Console для доменного ресурса требует настоящего отдельного TXT `google-site-verification=…` у авторитетного DNS-провайдера; SPF нельзя дополнять этим значением или заменять. Яндекс поддерживает HTML-файл/метатег с выданным им кодом. Добавляйте только полученные от сервисов коды, сохраняйте их после подтверждения. Sitemap можно обнаружить через robots.txt; отправка через кабинеты и запрос переобхода требуют авторизации и не гарантируют индексацию.

Подключена автоматическая очередь обновлений через Database Webhook → Edge Function → workflow_dispatch с Cron-повторами. Обновления автоматические с задержкой; ручной процесс выше остаётся доступен. Точные шаги, ограничения HTTP 404 и окно доступности скрытого HTML: [docs/catalog-static-sync.md](docs/catalog-static-sync.md).
